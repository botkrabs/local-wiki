# local_wiki — incident + upgrade handoff (2026-08-28)

## ✅ RESOLVED (2026-08-28 ~04:50) — root cause: a binding API footgun, NOT the files/FS/environment

`libzim.Query(text)` in the python-libzim 3.12.0 Cython binding **does not raise
and silently creates an EMPTY query** (the `Query` cdef class has no string ctor,
only `set_query()`; Cython's generated tp_new accepts the stray arg and ignores
it). Empty query → 0 results, no exception, ~6 ms, ~2 syscalls.

The original session benchmarked `Query(str)` (6 ms, actually an empty query)
vs `Query()+set_query()` (~550 ms, a REAL 8.3 GB FTS scan over cold 9p) and
mis-concluded the ctor form was a 90× speedup. `server.py` was switched to the
ctor form and restarted ~01:29 — that "regression" IS the incident. The WSL
clock jump was a coincident red herring.

Proven by a C++ probe compiled against the wheel's own libzim.so.9
(`zim::Searcher.setVerbose` + `search`): identical ZIM, correct results, parsed
query printed. Python `Query().set_query(...)` returns the same results.

**Fix**: `server.py` now uses a `_query()` helper = `libzim.Query().set_query(text)`
(see `_query` docstring). Server restarted with EN + zh, all green:
- EN search FTS: real hits, 0.19–0.5 s (miss path 0.54 s, was 1.63 s)
- zh full ZIM (13.7 GB, SHA256-verified): FTS works, 3.2 s cold / 0.18 s warm

**Verified during the misdiagnosis** (all still true, keep for reference):
- EN + zh + zh-mini ZIM files are byte-intact (SHA256 = official)
- No env/9p/clock/library issue; all libzim wheels 3.3.0–3.12.0 behave the same
- The zh physics MINI zim genuinely has NO FTS Xapian data on disk despite
  `_ftindex:yes` (mini build) — that test was a false alarm, now deleted
- libzim 9.8.1 (C++) + Xapian 1.4.23 glass-DB reader/writer are healthy
- mmap on 9p/drvfs is pathologically slow here (page-fault per read); raw
  read() is fast (~390 MB/s). libzim uses read() — fine.

Optional follow-up: report the `Query(str)` silent-empty footgun upstream
(openzim/python-libzim) — e.g. make the ctor raise TypeError.

## ⚠️ SECOND upstream bug found while fixing the zh miss-path (2026-08-28 ~11:00)

**C++ libzim 9.x drops `FLAG_DEFAULT` when parsing queries.** `src/search.cpp`
(9.0.0–9.8.x): `m_queryParser.parse_query(unaccentedQuery, Xapian::QueryParser::FLAG_CJK_NGRAM)`
— the 2-arg `parse_query` overload uses ONLY the flags given, so boolean ops
(OR/AND/NOT), `phrase:`, wildcards, parens, boosts are all silently ignored and
treated as literal words (default op is AND, set on the parser). 7.2.0 used the
1-arg form and worked. Proven live: `"einstein" OR zzqxwv` → est 0 (should be
~826); `phrase:"..."` → 0. Correct upstream fix: `FLAG_DEFAULT | FLAG_CJK_NGRAM`.

**Workaround in `server.py`**: `_cjk_loose()` — for CJK queries where the
strict AND query finds nothing, run one ranked query per overlapping 2-gram and
merge by co-occurrence (titles matching ≥2 grams rank first). Cost ~1.0–1.2 s
on the CJK miss path only. If a future libzim wheel fixes the flag bug, an OR
query could replace the merge, but the merge works either way.

Bench (post-fix, warm): EN 0.03–0.6 s, zh 0.03–0.3 s; zh miss→related now
returns real candidates (e.g. 大熊猫栖息 → 四川大熊猫栖息地).
